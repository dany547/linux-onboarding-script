# Linux onboarding — Debian, Ubuntu and Alpine

The Debian/Ubuntu Bash backend provides Docker Engine + Compose, Tailscale, UFW,
Fail2Ban, SSH hardening, security auto-updates and optional system upgrades, with
SSH access checks before firewall activation. The separate Alpine backend uses
POSIX sh, APK and OpenRC, with the narrower capabilities listed below.

Repository: https://github.com/dany547/linux-onboarding-script

Use `sh setup.sh` as the portable entry point. It selects the Debian/Ubuntu Bash
backend or the Alpine POSIX-shell backend; Alpine does not require Bash. Existing
Debian/Ubuntu invocations of `bash debian-setup.sh` remain supported. The options
below describe Debian/Ubuntu unless the Alpine section explicitly says otherwise.

## What it does

- `apt-get update` + `apt-get full-upgrade` (skip with `--skip-upgrade`);
- installs Docker Engine, Buildx and the Compose plugin from Docker's official
  `stable` repository (pinned OpenPGP fingerprint);
- installs Tailscale from its official `stable` repository (sign-in stays manual:
  `sudo tailscale up`);
- installs and configures UFW: `default deny incoming`, `default allow outgoing`,
  low logging, SSH allowed only from the configured networks, `IPV6=yes`;
- configures Fail2Ban for SSH (`sshd` jail, `banaction = ufw`, `ignoreip` = your
  allowed networks + current session);
- enables unattended security upgrades (distro security origin only unless
  `--update-third-party`);
- applies a minimal SSH baseline: no empty passwords, no X11 forwarding, limited
  auth retries, optional `AllowUsers` and key-only login;
- verifies Docker, Compose, Tailscale, UFW, Fail2Ban and the effective sshd config.

## What it does not do

- no inbound ports 80/443, no public port 22 in `--mode vps`;
- no Cloudflare Tunnel, WireGuard/WG-Easy, Linux users beyond `--create-user`,
  no automatic Docker port publishing, no `machine-id`/timezone/host-key changes;
- no generic OS hardening (sysctl, NTP, hostname, swap);
- it never runs on a Proxmox VE host (refused, exit 3).

Network restrictions describe rules generated by this script, not proof of
external reachability. Existing allow rules are retained unless explicitly reset;
preserved firewall state and provider/NAT policies are not changed or verified.

Docker's published ports bypass UFW: do not publish on `0.0.0.0` without an
explicit rule, and keep Cloudflare Tunnel apps on a shared Docker network instead
of `ports:`.

## Supported distributions

| System | Result |
|---|---|
| Debian 12 (bookworm), 13 (trixie) | supported |
| Ubuntu 22.04 (jammy), 24.04 (noble) | supported |
| Debian/Ubuntu derivatives (`ID_LIKE`) | accepted with an "untested combination" warning |
| Other codenames on a derivative | warning (repos may lack the suite) |
| Unknown codename on Debian/Ubuntu, Debian ≠12/13, Ubuntu ≠22.04/24.04 | refused, exit 3 |
| Alpine 3.24.x (latest stable checked: 3.24.2) | separate APK/OpenRC backend; see Alpine capabilities and validation below |
| RHEL family, Arch, anything else | refused, exit 3 |
| Proxmox VE host (`pveversion` found) | refused, exit 3 |
| Unprivileged LXC | UFW/Fail2Ban installation and configuration are skipped in the guest; existing installations remain unchanged — review host/infrastructure protection |

## Quick start — discover first (new machine)

```bash
git clone https://github.com/dany547/linux-onboarding-script.git
cd linux-onboarding-script

# 1. discover — read-only inventory: no root, no log file, no changes
bash debian-setup.sh --inspect

# 2. preview — prints the full plan, performs no change (may run as non-root)
sudo bash debian-setup.sh --dry-run -y --mode lan --lan-cidr 192.168.1.0/24

# 3. apply
sudo bash debian-setup.sh -y --mode lan --lan-cidr 192.168.1.0/24
```

Opt-in guided alternative instead of step 3 (interactive, conservative; cannot be
combined with `-y`):

```bash
sudo bash debian-setup.sh --wizard --mode lan --lan-cidr 192.168.1.0/24
sudo bash debian-setup.sh --wizard --dry-run --mode lan --lan-cidr 192.168.1.0/24   # wizard + plan only
```

VPS (SSH only over WireGuard/Tailscale, never publicly):

```bash
sudo bash debian-setup.sh --dry-run -y --mode vps --wireguard-cidr 10.8.0.0/24
sudo bash debian-setup.sh -y --mode vps --wireguard-cidr 10.8.0.0/24
```

Ready-made config files load with `--config` (CLI arguments win over the file):

```bash
sudo bash debian-setup.sh -y --config examples/lan.conf
sudo bash debian-setup.sh -y --config examples/vps.conf
sudo bash debian-setup.sh -y --config examples/vps-fleet.conf   # admin user + key + --ssh-keys-only
```

`--dry-run` as a normal user additionally needs `DS_ROOT_OK=1`.

## Alpine Linux 3.24 stable

The stable branch and patch were checked against the official
[Alpine release list](https://alpinelinux.org/releases/) and
[v3.24 release metadata](https://dl-cdn.alpinelinux.org/alpine/v3.24/releases/x86_64/latest-releases.yaml):
**3.24.2**. This is a tested branch target, not a promise to accept future stable
branches or Alpine edge automatically.

```sh
# On Alpine, as a normal user; no Bash installation needed:
sh setup.sh --inspect
sh alpine-setup.sh --help
sh setup.sh --wizard --dry-run

# Explicit package choices; preview first:
sh setup.sh --dry-run -y --config examples/alpine.conf
# Then, from a root shell on a BOOTED Alpine/OpenRC system:
sh setup.sh -y --config examples/alpine.conf
```

| Alpine capability | Behavior in 2.8.0 |
|---|---|
| Docker Engine + Compose | Opt in with `--docker` or `INSTALL_DOCKER=yes`; APK packages and OpenRC `docker` service |
| Tailscale | Opt in with `--tailscale` or `INSTALL_TAILSCALE=yes`; OpenRC `tailscale` service; run `tailscale up` manually as root |
| Discovery / wizard / preview | `--inspect`, `--wizard`, `--dry-run`; all choices default to preserve |
| Config files | Validated `KEY=value` data; CLI wins regardless of argument order; use `examples/alpine.conf`, not Debian fleet configs |
| Full package upgrade | Explicit `--upgrade` only; default is `--skip-upgrade`; may affect all installed services |
| SSH, firewall, Fail2Ban, users, auto-updates | Preserve-only; requests to configure these are rejected before package/service changes |

**`--mode lan` / `--mode vps` is informational on Alpine, not an access-control
policy.** This backend does not close public SSH or establish a firewall. Retain
and independently review existing host/provider protection. It does not implement
security-only automatic APK upgrades and will not replace them with an unsafe
cron job. All-preserved runs require no root, create no log and run no APK commands.
Applying selected services requires root and a booted OpenRC system; a minimal
container/chroot can inspect and preview, but is deliberately refused for apply.
`--upgrade` may run package maintainer scripts, so preserve does not exempt a
component from a separately requested full system upgrade.

Alpine uses its own signed APK repositories and OpenRC service scripts, not APT,
Debian repositories, systemd, or remote installer scripts. The Debian/Ubuntu
backend remains separate to avoid changing working platform behavior.

**Validation boundary:** official Alpine 3.24.2 x86_64 minirootfs was downloaded
and SHA256-verified. Package installation and CLI versions for Docker/Compose,
Tailscale and OpenSSH were checked in an isolated, rootless chroot. This does
**not** prove boot-time service activation, Docker daemon operation, VPN login or
remote SSH/firewall safety on a booted Alpine VM. See
[docs/ALPINE-VALIDATION.md](docs/ALPINE-VALIDATION.md) for evidence and remaining
booted-VM checks.

| `--dry-run` | Print the full plan (commands, files, UFW rules) with zero changes |
| `--inspect` | Read-only inventory: no root, no log file, no changes; exits after printing |
| `--wizard` | Conservative opt-in guided prompts; keeps existing services by default; works with `--dry-run`; cannot be combined with `-y` |
| `--no-ssh` | Do not modify the SSH service configuration (sshd drop-ins) |
| `--no-firewall` | Do not install/configure UFW or the UFW-based Fail2Ban integration |
| `--no-docker` | Do not install Docker Engine + Compose plugin |
| `--no-tailscale` | Do not install Tailscale |
| `--no-fail2ban` | Do not install/configure Fail2Ban |
| `--no-auto-updates` | Do not enable unattended security upgrades |
| `--reset-firewall` | Reset existing UFW rules first (backs up `/etc/ufw`) |
| `--allow-current-ssh` | Explicitly allow the current SSH session's IP |
| `--skip-upgrade` | Do not run `apt full-upgrade` |

| `--allow-users U1,U2` | `AllowUsers` in sshd; must include the current/created user |
| `--auto-reboot HH:MM` | Unattended reboot at the given time |
| `--mail ADDR` | Unattended reports by e-mail (needs a local MTA) |
| `--update-third-party` | Also auto-update the Docker/Tailscale repos |

| `-h`, `--help` | Print usage and exit |

## Configuration precedence and prompted choices

Precedence for values: **CLI > `--config` file > built-in default.** `--config` is
read in a first pass, so command-line arguments override the file regardless of
argument order. `--print-config` shows the resulting values.

A choice made on the CLI or in a config file (`--no-docker`, `--no-tailscale`,
`--no-fail2ban`, `--no-auto-updates`, `--no-ssh`, `--no-firewall`,
`--skip-upgrade`, …) is recorded as an explicit choice and **suppresses the
matching question** — neither the interactive prompts nor `--wizard` can reverse
it. Questions are asked only about choices that are still unspecified. Legacy
non-interactive (`-y`) and unattended defaults are unchanged: Docker, Tailscale,
Fail2Ban and security auto-updates stay on unless you disable them.

## `--wizard` (guided, opt-in)

`--wizard` is conservative and interactive: it shows a read-only inventory and the
detected package state first, then asks only about unspecified choices.

- Cannot be combined with `-y` (`--wizard -y` exits with code 2); it may be
  combined with `--dry-run`.
- Defaults are **No** for everything: SSH configuration change, firewall (UFW)
  configuration and the full system upgrade — pressing Enter keeps existing SSH
  and firewall access and skips `apt full-upgrade`.
- Component prompts (Docker, Tailscale, Fail2Ban, auto-updates) default to **No**
  and print the current package state; answering No means preserve/omit —
  **nothing is uninstalled**, and retained packages do not imply a global upgrade
  (only an explicit "upgrade all packages" answer, or a run without
  `--skip-upgrade`, performs `apt full-upgrade`).
- `--no-ssh` conflicts with `--ssh-keys-only` or `--allow-users`, and
  `--no-firewall` conflicts with `--reset-firewall` (both exit 2).
- The wizard states that **there is no timed rollback**: access-affecting changes
  are not automatically reverted after a delay or a lost session.
- Selecting no changes skips APT entirely. Otherwise applying may install base
  dependencies (ca-certificates, curl, gnupg, iproute2, python3-minimal, sudo),
  plus `openssh-server` when SSH is managed, `ufw` when the firewall is managed,
  and `python3-systemd` for the selected UFW/Fail2Ban integration.
- The final apply confirmation defaults to **No** in wizard mode. Dry-run and apply
  ask the same configuration questions, but answers are not saved between runs.
- Conservative/preserve modes ask needrestart to list rather than automatically
  restart unrelated services. Package maintainer scripts can still restart them.

## `--no-ssh` and `--no-firewall`

- `--no-ssh` protects only the **sshd service configuration** (no drop-ins, no
  `AllowUsers`, no key-only policy). It does **not** cancel user or key
  provisioning you asked for explicitly: `--create-user`, `--ssh-key-file` and
  `--ssh-key` are still applied.
- `--no-firewall` skips installing and configuring UFW **and** the UFW-based
  Fail2Ban integration (Fail2Ban install/config and the `ufw` base package are
  skipped with it). Existing firewall state is left alone; the script does not
  establish or verify protection in this mode. Review existing host/infrastructure
  enforcement yourself.

## SSH and firewall guards

The lockout guard refuses to enable UFW when the current session's source is not
covered by the proposed rules (exit 4). Session detection order:
`SSH_CONNECTION` → `sshd`/`sshd-session` PPID chain + `ss` → `who -m`.

- On a fresh VPS, run it **from the provider console first**, not over SSH.
- Escape hatches: `--allow-current-ssh`, `DS_SSH_SOURCE=IP`, or a correct
  `--lan-cidr` / `--wireguard-cidr`. With `-y` and an uncovered session the run
  stops with exit 4; interactively you must confirm explicitly.
- `--allow-current-ssh` also covers other *established* SSH sessions (tmux/screen
  chains that hide the ancestor) — each gets a /32 (or /128) rule.
- `--ssh-keys-only` is a hard precondition: at least one privileged account must
  already hold a valid key (or be created with a key in the same run), otherwise
  exit 4; likewise if `--allow-users` excludes every key-capable account.
- No allowed network at all → exit 4.
- With `--no-firewall` no UFW change is made at all, so these firewall guards and
  the allowed-network list do not apply to that run; `--no-ssh` leaves sshd
  untouched. Neither disables the final confirmation prompt.
- LAN mode allows SSH from `--lan-cidr`, `--wireguard-cidr` and Tailscale
  (`100.64.0.0/10` + `fd7a:115c:a1e0::/48`); VPS mode opens no public SSH port.

## Running on an existing host

There is **no guaranteed rollback and no timed rollback.** The script has no revert transaction: package
installs, `apt full-upgrade`, sshd drop-ins, user/sudoers changes and enabling UFW
are not automatically undone if something later fails or you lose access. The only
safety nets are targeted, per-change copies: `/var/backups/ufw-<timestamp>/` on
`--reset-firewall`, `daemon.json.bak-<timestamp>` before each daemon.json edit, and
automatic restore of the ssh drop-ins when `sshd -t`/`sshd -T` fails.

Practical advice for machines that already matter:

- review `--dry-run` output line by line and take your own snapshot/backup first;
- `--reset-firewall` deletes every existing UFW rule — only use it when you intend
  to rebuild the firewall from scratch (without it, existing rules are kept and the
  summary warns about it);
- `--ssh-keys-only`, `--allow-users` and `--create-user` change who can log in;
  keep a second access path (console/Tailscale/WireGuard);
- Docker/Tailscale come from external `stable` repos; their upgrades are only
  included when `--update-third-party` is set.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | success (also user-aborted before any change) |
| 1 | runtime error (e.g. bad key fingerprint, invalid JSON, `--strict` verification failure) |
| 2 | invalid arguments/configuration, missing option value, test `DS_*` overrides present |
| 3 | unmet precondition / unsupported OS / Proxmox / not root |
| 4 | detected lockout risk |

## Environment overrides

- `DS_SSH_SOURCE=IP` — declare the SSH session source when detection cannot (e.g.
  deep `sudo`/`su` chains). Safe in production.
- Test/CI only: `DS_TEST=1`, `DS_OS_RELEASE`, `DS_ROOT_OK`, `DS_SSH_CHAIN`,
  `DS_SSHD_PID`, `DS_CMD_*`, `DS_UFW_DEFAULT`, `DS_DOCKER_DAEMON`,
  `DS_SSH_CONFIG_DIR`, `DS_TAILSCALE_OLD_LIST`, `DS_SUDOERS_DIR` — see the script
  header. On a real run (not `--dry-run`, not `DS_TEST=1`) any `DS_*` variable
  aborts with exit 2. The same test-override guard applies to `--inspect`, even
  though inventory is read-only. `DS_ROOT_OK=1` only relaxes the root check for
  `--dry-run`.

## Logs, verification, containers

- Log: `/var/log/debian-setup.log` (no colors; `trap ERR` records line + command).
- After a run: `docker --version`, `docker compose version`, `sudo tailscale status`,
  `sudo ufw status verbose`, `sudo fail2ban-client status sshd`, `ss -lntup`.
- Unprivileged LXC: UFW/Fail2Ban stay off in the guest; Docker may need
  `nesting=1`, `keyctl=1`, `fuse=1`.
- Auto-updates verify that `unattended-upgrade --dry-run --debug` lists the distro
  security origin; a failed check is a loud warning, or exit 1 with `--strict`.
  The script does not reboot immediately. `--auto-reboot` explicitly enables
  later unattended reboots; otherwise check `/var/run/reboot-required` manually.

## Tests and validation status

```bash
bash tests/run.sh       # unit tests: non-root, no network, temp fixtures are cleaned up

```

The suite is **mocked**: fixtures replace `/etc/os-release`, UFW, `sshd`, `ss` and
friends. The manual real-VM checklist in `docs/TEST-VM.md` (Debian 12/13, Ubuntu
22.04/24.04, privileged and unprivileged LXC) has **not been executed for this
baseline**, so this release makes no real-VM or production-readiness claim.
